# KeyState Stage 2 — z_entry_descriptor Targets

## Scope

This stage adds an auxiliary prediction path for a future/current checkpoint-window entry descriptor. The training-side plumbing is shared by two descriptor-generation backends:

- `bootstrap_dct_v1`: deterministic hand-crafted visual descriptor used only to validate the Stage2 data path and `loss_z_entry_descriptor` training signal.
- `frozen_pi0_prefix_projected_v1`: frozen Pi0/PaliGemma prefix hidden target, projected to 64 dimensions. This is the prefix-only baseline.
- `frozen_pi0_action_expert_demo_t0001_projected_v1`: frozen Pi0 action-expert hidden target at the checkpoint entry, projected to 64 dimensions. This is the current main Stage2 key-state latent backend; it is computed from observation, instruction, robot state, and the demonstration action-generation context.

The field name remains `z_entry_descriptor` for both backends so the processed-HDF5, LeRobot, DataLoader, and model-loss path can stay identical. Always check the HDF5 metadata attr `z_entry_descriptor_encoder` before interpreting an experiment.

Stage0's existing `next_checkpoint_type` field is kept for compatibility, but its intended semantics are now documented as **current-or-next checkpoint type**: before a checkpoint window it points to the upcoming window; inside a checkpoint window it identifies the current high-risk window. Together with `h_entry`, this preserves the adaptive-execution signal `type > 0 and h_entry == 0` for "currently inside a checkpoint window".

Stage2 still does **not**:

- feed `z_entry_descriptor_hat` into the action expert;
- modify `embed_suffix()` action conditioning;
- modify `sample_actions()` inference behavior;
- modify RoboTwin deployment/adaptive execution.

## Data contract

### Raw RoboTwin HDF5

Generated by `policy/pi0/scripts/generate_keystate_z_entry_descriptors.py`:

```text
/keystate/z_entry_descriptor      float32 [T, 64]
```

Metadata attrs on `/keystate`:

```text
z_entry_descriptor_dim
z_entry_descriptor_encoder        "bootstrap_dct_v1", "frozen_pi0_prefix_projected_v1", or "frozen_pi0_action_expert_demo_t0001_projected_v1"
z_entry_descriptor_source         "entry"
z_entry_descriptor_normalized     true
z_entry_descriptor_version        1 for bootstrap, 2 for frozen-Pi0 prefix, 3 for frozen-Pi0 action expert
z_entry_descriptor_entries        JSON map of checkpoint type -> entry frame
z_entry_descriptor_supervision    "pre_entry_only_h_entry_gt_0"
```

For frozen Pi0 backends, additional attrs are written:

```text
z_entry_descriptor_source_dim     original hidden dim, e.g. 2048 for prefix or 1024 for action expert
z_entry_descriptor_projection     "fixed_random_projection_v1"
```

For `frozen_pi0_action_expert_demo_t0001_projected_v1`, additional attrs are written:

```text
z_entry_descriptor_hidden_source  "action_expert_suffix_out_action_tokens_mean"
z_entry_descriptor_action_context "demo_action_chunk"
z_entry_descriptor_timestep       0.001
```

`z_entry_descriptor` is supervised only before the robot reaches the checkpoint-window entry:

```text
h_entry > 0   -> descriptor is the upcoming window-entry latent, z loss ON
h_entry == 0  -> descriptor is zero, z loss OFF because the robot is already inside the window
h_entry == -1 -> descriptor is zero, z loss OFF because no current/future window exists
```

The model loss masks zero descriptor targets via the target-norm check.

Frames with no next/current checkpoint target (`next_checkpoint_type == 0`, `h_entry == -1`) are written as zero vectors and masked out by the model loss.

### Processed HDF5

Propagated by `policy/pi0/scripts/process_data.py` when present:

```text
/observations/keystate/z_entry_descriptor      float32 [N, 64]
```

It follows the existing current-frame alignment used by Stage1 labels: raw frame `j` is copied when `j != last`, so `N = T - 1` alongside `qpos`.

### LeRobot dataset

Registered by `policy/pi0/examples/aloha_real/convert_aloha_data_to_lerobot_robotwin.py` when present:

```text
observation.keystate.z_entry_descriptor        float32 [64]
```

### Model observation

Mapped by `openpi/policies/keystate.py` into:

```text
Observation.keystate_z_entry_descriptor        float32 [B, 64]
```

## Descriptor generation

### Bootstrap backend

Dry run:

```bash
cd third_party/RoboTwin
policy/pi0/.venv/bin/python policy/pi0/scripts/generate_keystate_z_entry_descriptors.py \
  --task place_a2b_left \
  --config demo_clean \
  --data-root data \
  --episode 0 \
  --encoder bootstrap_dct_v1 \
  --dry-run
```

Write descriptors:

```bash
policy/pi0/.venv/bin/python policy/pi0/scripts/generate_keystate_z_entry_descriptors.py \
  --task place_a2b_left \
  --config demo_clean \
  --data-root data \
  --episode 0 \
  --encoder bootstrap_dct_v1 \
  --overwrite
```

`bootstrap_dct_v1` decodes the entry-frame cameras, computes small RGB/statistical + low-frequency DCT features, applies a fixed deterministic projection to 64 dimensions, and L2-normalizes the result. It is not a frozen Pi0 latent and should not be used as the final paper result.

### Frozen Pi0 prefix projected backend

Write frozen Pi0 prefix targets:

```bash
export OPENPI_DATA_HOME=./checkpoints/openpi
export XLA_PYTHON_CLIENT_MEM_FRACTION=0.90
export XLA_PYTHON_CLIENT_PREALLOCATE=false

policy/pi0/.venv/bin/python policy/pi0/scripts/generate_keystate_z_entry_descriptors.py \
  --task place_a2b_left \
  --config demo_clean \
  --data-root data \
  --episode 0 \
  --encoder frozen_pi0_prefix_projected_v1 \
  --target-config pi0_base_aloha_robotwin_lora \
  --z-dim 64 \
  --overwrite
```

If you want to use a specific local checkpoint instead of the config default weight loader, pass:

```bash
  --target-params-path ./checkpoints/example/params \
  --target-missing-regex '.*lora.*'
```

The backend builds the target config model, loads its weight loader (or the explicit target params), transforms the raw entry observation through the Aloha + image resize + PaliGemma tokenizer input path, runs the frozen Pi0 prefix stack, masked-mean-pools prefix hidden states, applies deterministic random projection to 64 dimensions, and L2-normalizes.

### Frozen Pi0 action-expert key-state latent backend

Write action-expert key-state latent targets:

```bash
export OPENPI_DATA_HOME=./checkpoints/openpi
export XLA_PYTHON_CLIENT_MEM_FRACTION=0.90
export XLA_PYTHON_CLIENT_PREALLOCATE=false

policy/pi0/.venv/bin/python policy/pi0/scripts/generate_keystate_z_entry_descriptors.py \
  --task place_a2b_left \
  --config demo_clean \
  --data-root data \
  --episode 0 \
  --encoder frozen_pi0_action_expert_demo_t0001_projected_v1 \
  --target-config pi0_base_aloha_robotwin_lora \
  --z-dim 64 \
  --overwrite
```

This backend defines `z_entry` as a checkpoint-entry key-state latent extracted from the frozen Pi0 action expert. It uses the checkpoint entry observation, instruction, robot state, and demonstration action chunk, runs the frozen action expert with timestep `0.001`, pools `suffix_out[:, -action_horizon:]` over action tokens, projects the resulting action-expert hidden to 64 dimensions, and L2-normalizes it.

The training model predicts this key-state latent from its own action-expert hidden. Stage2 still keeps the z head auxiliary: the predicted z is not fed back into action generation in Stage2.

Validation on `place_a2b_left` one-shot:

```text

processed descriptor: shape=(151, 64), pre-entry nonzero frames=77, window zero frames=74
LeRobot repo_id: place_a2b_left_keystate_z_entry_descriptor_actionexpert_oneshot
```

```text

```

1000-step one-episode overfit:


## h_entry bucket contract

Stage2 uses the same horizon bucket contract as Stage1 for `loss_h_entry`:

```text
bin 0: h_entry == 0                 # inside checkpoint window
bin 1: 1 <= h_entry < 4             # very near entry, still before window
bin 2: 4 <= h_entry < 7
bin 3: 7 <= h_entry < 11
bin 4: 11 <= h_entry < 21
bin 5: 21 <= h_entry < 51
bin 6: h_entry >= 51
invalid: h_entry < 0
```

The code config is:

```python
horizon_upper_edges = (1, 4, 7, 11, 21, 51)
```

This only changes the horizon-head target dimension from 6 to 7 bins. It does **not** change z-entry descriptor generation: z supervision still follows the raw `h_entry` rule `h_entry > 0` ON, `h_entry == 0/-1` OFF.

Use the histogram helper before retraining on a new dataset:

```bash
cd third_party/RoboTwin/policy/pi0
.venv/bin/python scripts/inspect_keystate_h_entry_buckets.py \
  processed_data/place_a2b_left-stage2_actionexpert_tmp-1
```

## Training config

Stage2 uses:

```text
pi0_base_aloha_robotwin_keystate_stage2_lora
```

This config enables:

- Stage1 checkpoint type and h-entry heads.
- Stage1 semantic phase head.
- Stage2 descriptor head (`use_z_entry_descriptor=True`).
- `loss_z_entry_descriptor` with weight `lambda_z_entry_descriptor=0.1`.

The new loss is returned through the existing `ks_losses` dict, so `scripts/train.py` automatically adds it to total loss and logs it.

Use different LeRobot repo IDs to avoid mixing target backends, e.g.:

```text
place_a2b_left_keystate_z_entry_descriptor_bootstrap_oneshot
place_a2b_left_keystate_z_entry_descriptor_actionexpert_oneshot
```

## Validation checklist

1. Generate descriptors and inspect raw HDF5:
   - `/keystate/z_entry_descriptor` exists.
   - shape is `[T, 64]`, dtype is `float32`.
   - metadata attr `z_entry_descriptor_encoder` identifies the backend.
   - frames with `h_entry > 0` have unit-norm descriptors.
   - frames with `h_entry == 0` or `h_entry == -1` have zero descriptors and therefore no z loss.
2. Process data and inspect processed HDF5:
   - `/observations/keystate/z_entry_descriptor` exists.
   - first dimension matches `/observations/qpos`.
3. Convert to LeRobot:
   - metadata includes `observation.keystate.z_entry_descriptor`.
4. DataLoader smoke:
   - `Observation.keystate_z_entry_descriptor` has shape `[B, 64]` and finite nonzero norm on valid frames.
5. Train smoke:
   - 2-step Stage2 run logs finite `flow_loss`, `loss_type`, `loss_h_entry`, `loss_ph`, `loss_z_entry_descriptor`, and total `loss`.
6. One-episode overfit:
   - `loss_z_entry_descriptor` decreases.
   - Existing Stage1 losses remain finite.

## Limitations

On one-episode data, there may be only two distinct checkpoint-entry descriptors. A short overfit run validates implementation plumbing and optimization but is not evidence of generalization. The frozen Pi0 projected backend should be used for paper-facing Stage2 experiments; the bootstrap backend is for debugging and ablation sanity checks only.
